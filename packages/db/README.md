# Database foundation

Migration 202610230001 creates profiles, workspaces, members, projects, albums and photos, with read-only tenant RLS, composite tenant foreign keys and safe retention defaults. It deliberately does not implement the rest of DATA_MODEL.md. M1 workspace APIs read through tenant RLS and write only through reviewed RPCs. Owners can read their workspace; active members can read joined workspaces. Direct table writes remain forbidden. Anon has no grants. Keep the security-definer function owned by the migration administrator.

Use a NEW local/staging Supabase database (auth.users, auth.uid(), anon and authenticated must already exist). Back up first using Supabase backups or pg_dump. Set DATABASE_URL in the shell, then `pnpm db:migrate`. The runner applies all pending SQL in one transaction, locks concurrent runners and refuses changed historical checksums. Do not disable TLS for a remote database. Rerun is safe. Production application rollout is blocked until real Supabase/RLS tests pass.

Recovery: failed migrations roll back atomically. After successful application, prefer a forward corrective migration. To restore data, stop writes and restore the pre-migration backup into a separate database, validate counts/RLS, then switch the connection. Do not DROP tables on a populated database. For an empty disposable local DB, recreate the entire local DB and replay migrations; no automatic down command is supplied.

Tests use PGlite (embedded PostgreSQL) with test-only auth role/function shims. This executes real SQL/RLS but does not validate hosted Supabase Auth, PostgREST, network, extensions or production roles. Run the same isolation cases against local/staging Supabase before M1 sign-off.

## Migration 202610230002 — identity/workspace slice

Additive: private idempotency records, public append-only audit_logs, owner check, ensure_photographer_profile, create_workspace, set_workspace_member. Supabase auth.identities must exist in addition to auth.users/auth.uid. Function ownership must remain the trusted migration administrator. No service-role key is used by the app. Only authenticated Google identities may call write RPCs. Workspace provisioning creates profile/owner membership/audit within the same transaction. Actor+requestId replays identical payload; changed payload/operation returns conflict. A per-user row lock enforces the 100 owned workspace application limit. Membership updates lock the workspace, require its owner, prohibit changing the owner role and allow only existing platform profiles. Suspended members lose RLS access. The audit trigger rejects UPDATE/DELETE, including accidental administrator mutations; privacy maintenance is a later, separately authorized procedure.

Recovery: all migration statements are within the existing runner transaction, so failure rolls back. Back up before applying; after application, prefer forward fixes and restoring the pre-migration snapshot into a separate DB when needed. To immediately disable new write entrypoints during an incident, a DB administrator may REVOKE EXECUTE from authenticated on the three RPC signatures (listed in SQL). This preserves all data, audit and read policies. It is a maintenance action, not an automatic rollback. Do not drop audit_logs, reset migration checksums or delete idempotency rows on a populated DB. Local throwaway databases may be recreated and replayed. No hosted migration/recovery has been executed here.

## Migration 202610230003 — identity hardening

Add a statement-level audit TRUNCATE rejection and replace create_workspace's per-user lock with FOR NO KEY UPDATE (same provisioning serialization, compatible with profile FK KEY SHARE). No rows removed and no auth permission expansion. Recovery: revoke create_workspace EXECUTE if needed, retain all tables/audit, apply reviewed forward fix; do not remove the audit trigger or edit applied migration checksums. Multi-session PostgreSQL contention still requires staging verification.

Reference: https://www.postgresql.org/docs/current/explicit-locking.html and https://www.postgresql.org/docs/current/sql-createtrigger.html .

## Migration 202610230004 — project/album create and rename

Adds positive integer revisions (existing rows start at 1), an album pagination index, immutable ID/workspace/parent triggers, and create_project/rename_project/create_album/rename_album RPCs. It does not expose delete, status transitions, publication, pin/legal-hold changes or retention policy controls. Existing direct-write denies and RLS remain. Owner, active workspace_editor and photographer may write; retoucher may read only. Missing/inaccessible resources return NOT_FOUND; a visible read-only member gets FORBIDDEN_SCOPE on mutation.

Every write verifies a current Google identity, takes the request advisory lock then the workspace NO KEY UPDATE lock, checks current role before replay, and locks the target resource before revision comparison. Membership mutation locks the same workspace, serializing revocation against writes. The global actor/request namespace is shared with workspace operations. Exact replay returns its original result without another mutation; changed operation/payload conflicts. Rename requires expectedRevision; any accepted new rename request, even the same normalized name, increments revision and appends an event. Stale revision changes nothing. Resource update, before/after audit and idempotency result commit or roll back together. Immutable associations reject maintenance reparenting; any future move needs a separately reviewed migration/workflow.

Recovery: apply using the transaction/checksum runner after backup. A failed migration rolls back. For an incident, an administrator may REVOKE EXECUTE from authenticated on the four new RPC signatures to stop content writes while preserving reads and data. Prefer a forward fix; restore a backup into a separate database and verify RLS/counts before switching if required. Do not drop revision columns or immutable triggers on populated production, edit old migrations, or delete audit/idempotency history. Disposable test databases can be recreated. PGlite tests exercise real SQL but cannot prove multi-session PostgreSQL races or hosted Supabase privileges; those remain an external acceptance gate.

## Migration 202610230005 — workspace Unicode names

Replaces create_workspace without changing its actor checks, locks, quota limit or transaction behavior. Validation, idempotency payload and stored names now use the same Unicode trim helper as project/album RPCs and the same 1–120 code-point length as the input/response contract. This prevents a directly authenticated RPC request from storing an invisible whitespace name or an astral-character name that breaks subsequent API parsing. Existing records, audit and idempotency history are not rewritten.

Recovery: the migration runner applies this replacement transactionally; failure restores the previous function automatically. After successful application prefer a forward fix. An administrator may revoke authenticated EXECUTE on create_workspace(text,uuid) to stop provisioning without altering existing data; restore any backup into a separate verified database. Do not edit older migration checksums or rewrite historical request/audit records to alter name normalization. Any historical invalid whitespace rows require a separately reviewed, audited corrective migration; this change only prevents new invalid writes.

## Migration 202610230006 — OAuth providers and explicit link intent

Add require_oauth_user (Google/GitHub auth.identities by auth.uid); retain require_google_user as a compatibility wrapper for deployed RPC bodies. No existing user ID, profile or tenant ownership changes. Add private RLS-protected oauth_link_intents and three controlled RPCs: begin_oauth_link/read_oauth_link/complete_oauth_link. Only token hashes are stored, scoped to current actor, ten-minute expiry, at most five pending intents; start/completion append audit, completed intent retries do not append twice. Audit failure rolls back app intent state/ledger; actual provider-side identity linking is a separate Auth operation and is not undone by the app transaction.

Recovery: migration runner transaction/checksum protections apply. Back up first; on incident set AUTH_MANUAL_LINKING_ENABLED=false and an administrator can revoke authenticated EXECUTE on the three new RPC signatures to stop app linking while preserving users, reads and data. Apply a reviewed forward fix. Do not drop auth.identities, unlink providers, reassign workspace owners, delete logs/intents, revert to a Google-only guard (would lock out GitHub-only users), or modify historical checksums. Restore a coherent Auth/DB backup into a separate verified environment if required. No hosted migration/restore executed. Private intent retention/operational cleanup and auth-provider reconciliation are future maintenance work.

## Migration 202610230007 — Owner-controlled album protection

Adds only `set_album_protection(uuid,boolean,boolean,integer,boolean,uuid)`; existing album flags are reused, no table or data rewrite. Verified Google/GitHub actor; request advisory → workspace → album locks; current owner authorization before replay; shared revision CAS with rename; non-null booleans; explicit confirmation to clear an existing flag; deleting/deleted reject changes. Mutation, before/after audit and private global request ledger commit together. Historical replay returns its original result without restoring old flags. Same-value fresh requests increase revision and audit once.

Recovery: migration runner wraps creation/ACL in its normal transaction; on failed migration no partial function/ACL remains. After successful application, prefer a forward fix. An administrator may `REVOKE EXECUTE ON FUNCTION public.set_album_protection(uuid,boolean,boolean,integer,boolean,uuid) FROM authenticated;` to stop changes. Preserve flags/audit/request history; do not clear protection or rewrite old migration checksums. Restore a coherent backup to a separate verified database if required. No hosted migration/restore has been run. Future retention executors must take the same workspace/album locks and recheck flags before marking deleting; this migration does not supply a deletion executor.
