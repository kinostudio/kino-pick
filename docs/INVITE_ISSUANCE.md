# M2d — Local Owner invitation issuance and secret-safe recovery

Implemented backend slice: strict contracts, immutable0019 command spine, all-three-mode issuer, Owner POST/recovery GET and actual D1/Chromium tests. M2g adds the separate Guest exchange backend behind a local-only/default-OFF gate; M2k adds local creation/share and Guest entry UI; no hosted-ready workflow is claimed. See INVITATION_FLOW.md. Existing Owner list/revoke UI remains functional.

## Gate and request

GUEST_INVITE_ISSUANCE_ENABLED defaults false and is explicitly false in local/staging/production Wrangler vars and .dev.vars.example. A NEW issuance requires the flag true AND APP_ENV=local; staging/production cannot enable new issuance with this flag. Only isolated synthetic tests set it true in this increment. Guest exchange is implemented only behind the local-only/default-OFF gate; hosted KDF CPU/memory/concurrency/throttle acceptance remains unfinished. Metadata-only committed replay/recovery is allowed while creation is disabled.

POST /api/v1/projects/:projectId/invites requires current enabled Owner/live session, exact Origin, JSON and16KiB body cap. Strict input: requestId UUID,1–24 distinct albumIds UUIDs, accessMode link_only/generated_password/custom_password, full12-boolean permissions, expiresAt UTC ISO and maxUses nullable1–10000. password is present only for custom_password and must pass GUEST_CREDENTIALS bounds. Album order is canonicalized; expiry is normalized to integer milliseconds. No caller token/hash/verifier/actor/session/tenant is accepted. New scope must belong to the owned unarchived project and every album must be active; SQL repeats checks after KDF. Expiry is after DB now and at most365days; local conservative project limit1000 stored invitations. No version/photo/storage/quota writes.

200 response is discriminated by secretAvailable. First proven winning invocation may return {invite:{inviteId,workspaceId,projectId,createdAt,expiresAt},secretAvailable:true,token,generatedPassword}; generatedPassword is a new independent256-bit hex password only for generated mode, otherwise null. Custom passwords are never echoed. link_only still has a random bearer token; it means no password, not public enumeration. The API returns no share URL; M2k local UI builds per-album fragment-only entry links from the initial winning response. Secret response is private/no-store/no-referrer.

Exact replay returns only {invite,secretAvailable:false}. GET /api/v1/invites/creation/:requestId returns the same metadata-only shape under current Owner/session, including while flag is off or the project/invite is archived/expired/revoked. Missing/foreign request404. It never returns stored token hash, verifier, commitment, original password or regenerated token. New disabled issuance503 INVITE_ISSUANCE_DISABLED; malformed input400, anonymous401, Origin/Owner403, unknown/foreign parent404, conflicting request/scope/expiry/limit409, unknown result503. Nested INVITE_EXPIRED is mapped409 because that transaction rolled back.

## Commit and one-time secrets

invite_creation_commands is the single SQL mutation spine. Its guard checks current Owner/session, all five older Owner ledgers, same-request payload/commitment conflict, exact replay, then creation eligibility. One command INSERT inserts invite, exact scope, seal and request-correlated share.created/share.scope_sealed audit. Audit/seal failure rolls back every row. Five older canonical guards are rebuilt to include the new ledger before local RAISE(IGNORE), preserving all original operation checks; no sibling-trigger ordering dependency. Existing data/audit is unchanged.

Each candidate invocation generates a fresh UUID/token and optional random password/salt. The response reveals credentials only when D1 reports positive meta.changes AND the committed command has that candidate UUID AND its token hash/verifier matches this invocation. Fixed-length secret comparisons are timing-safe. An ignored/concurrent loser, unknown write outcome or missing proof never returns its locally generated secrets. Stored command has only random-token hash, salted verifier and keyed request commitment; never plaintext/reversible credential storage. Lost successful response cannot be recovered by replay and does not silently create another invite.

Actual Chromium drops the first committed response, retries the same request body/ID, obtains secretAvailable:false, and confirms recovery GET returns identical metadata. Owner can explicitly revoke that committed invite using M2b, then choose a new operation if credentials are lost. Do not label the original outcome a definite failure or automatically issue another ID. No durable browser secret cache is introduced.

## Password commitment and rotation

Sanitized canonical config is stored separately from credentials. Replay equality uses HMAC-SHA256 under BETTER_AUTH_SECRET over an unambiguous JSON array containing versioned kino-pic:invite-create-request:v1 domain, actor, request ID, canonical config/project and exact validated custom password (null for other modes). This binds a changed password to REQUEST_ID_CONFLICT without putting it in command JSON/audit or using a bare password SHA hash. All modes use the same versioned commitment envelope; verification is timing-safe. Commitment/hash/verifier columns remain server-private and are excluded from lists/recovery/audit.

The commitment key is not versioned separately in this increment. Rotating BETTER_AUTH_SECRET makes old POST commitments conflict; after renewed Owner login, use metadata-only recovery GET, which does not need the old commitment key. Never recover/re-hash an old plaintext password or silently recreate the invite. Supporting cross-key POST replay later requires an explicit versioned key-retention policy; not claimed here.
