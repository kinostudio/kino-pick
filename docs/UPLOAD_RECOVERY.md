# Upload reload recovery — CF-03c5

## Implemented flow

The Owner upload queue now restores bounded metadata in the same browser/account/workspace/project/album. Reload or collapsing the panel does not silently restart a PUT. Open the album upload panel and choose Confirm recovery status. A new read-only API finds the current upload through the original init request ID, including when the init response was lost. Completed/cancelled/expired/review states need no file. A previously authorized reservation can attempt its saved completion ID first to reconcile an already-received original. Only an explicit reselection plus a fresh browser decode/hash match can enable another PUT.

Reselection compares canonical trimmed filename, exact size, detected MIME, SHA-256 and dimensions. A valid image with the same filename/size/dimensions but a different hash is rejected without sending it. Recovering a cancellation skips completion reconciliation: server cancellation preserves any existing original and offers confirmation when appropriate. No new reservation or operation ID is automatically substituted for an uncertain outcome.

## Journal and authority

`upload-journal.ts` uses a strict version1 allowlist,20 items and64KiB UTF-8 per account+album scope. It stores init scope/name/size/type/hash, dimensions, local row UUID, workflow session UUID and init/authorize/complete/cancel operation UUIDs. It never stores File/image bytes, preview/blob/data URL, upload URL/authorization response, OAuth/session cookie or credentials. Duplicate item/operation IDs, wrong scope, oversized/corrupt records and records older than7 days since last write are rejected. Seven days is a recovery window after last metadata update, not an upload-authority lifetime or an automatic physical-deletion promise. Expired/corrupt records require explicit local clearing; that action does not cancel server work, remove objects or release quota. Confirmed terminal entries are removed from the journal.

IDs are persisted before their first mutation. Write failure blocks subsequent mutations and PUTs; a request already in flight may have committed, so keep the existing journal and resolve via the original ID. Initial storage failure also blocks upload rather than claiming persistence. This feature requires usable localStorage and Web Locks in a secure/loopback context; unsupported browsers show a real unavailable state. Journals across many albums still share browser storage limits. Clearing/eviction of the whole browser record loses local discovery; a server pending-work list/reconciliation remains future work.

Fresh `/api/v1/me` chooses the actor namespace before restore and before mutation/PUT. The browser includes X-Kino-Expected-Actor on init/authorize/complete/cancel; the Worker checks it against the authenticated Owner before route writes. This header is an expectation, not authentication; ordinary current-session/tenant/Origin checks still apply and legacy callers without it retain those checks. It is never forwarded to R2. Recovery compares authoritative session/scope/name/size/MIME/hash before resuming or cancelling. Cached metadata is advisory, never authority.

One exclusive Web Lock is held per full actor/resource scope while the panel is open. A second tab is blocked until the first panel closes; this avoids two journal writers, while backend idempotency/create-only R2 remains the ultimate data safeguard. Queue generations, exact scope checks and a full-scope React key prevent delayed callbacks from continuing after teardown/replacement. The real delayed-init test collapses/reopens the panel before acknowledgement, then proves the old instance sends no authorize/complete and the recovered session can be cancelled once.

## Read-only API

GET `/api/v1/uploads/recovery/:initRequestId` returns `{initRequestId,uploadSession,contentType,sha256,authorizationRequestId,authorizationExpiresAt}`. uploadSession is the full canonical existing session shape; nullable fingerprint/auth fields accommodate legacy metadata and fail closed for new PUT recovery. Current Owner/session and original request ownership are joined in the D1 read. Invalid UUID400, unknown/foreign/non-init request404, anonymous401, disabled Owner403. Response is private/no-store and contains no object key, signed URL, auth-session ID or credential. Unlike the older status GET, this endpoint does not run the unissued-expiration sweep or mutate any state/audit/quota.

## Expiry and remaining gates

Recovering metadata does not renew a signed upload authorization. Existing authorization remains an immutable replay only within its original window; no renewal operation or multipart/byte-range resume was added. If a valid original is already present, completion is reconciled first. If it is missing and the original authority has expired, the UI stops and offers cancellation/manual handling; only after the old work resolves may the user explicitly add the file as a new operation. Expiration/cancellation still requires the existing permanent-fence rules before quota release; no HEAD miss or local cache deletion is proof for release.

No migration/schema change:0015 remains latest. Roll back this increment only to a bundle still compatible with0015 abandoned jobs/ledger; retain journals, immutable assets, quotas and audit. Code rollback does not repair or reset server counters. Upload/multi-account/autodelete flags remain OFF, retention dry-run ON, no new credentials/bindings or remote data/deployment. Actual local tests use workerd/D1/R2, a signature-verifying intercepted S3 bridge and synthetic OAuth; they are not live provider/CORS/HTTPS evidence. The standalone local bridge/provider limitation from PROCESSING_PIPELINE still applies.
