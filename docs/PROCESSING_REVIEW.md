## Explicit confirmation and safe retry

POST `/api/v1/photos/:photoId/versions/:versionId/processing-review/abandon` accepts only `{requestId,expectedLeaseEpoch,confirmAbandon:true}`. Current Owner/session, same-origin JSON,16KiB body cap, exact job/photo/version and review epoch are required. The UI first shows the actual Dry Run, requires an unchecked explicit confirmation and explains permanent stopping of this derivative recipe while retaining the original. Success refreshes the real gallery to `abandoned`. Network/unknown responses retain the same request ID/epoch for retry; inspection does not erase the pending operation. Reload-resume of this intent is not yet implemented.

The trusted service derives both keys from immutable D1 slots, checks primary node active/current editable scope, then conditionally creates permanent empty markers at both outputs. Exact marker identity requires zero bytes, provider-verified empty SHA-256, dedicated MIME and matching job/kind metadata. Puts use raw Web Crypto digest buffers. Lost acknowledgements require readback. No existing object is overwritten or deleted. Any occupied key gives409 PROCESSING_OUTPUTS_OCCUPIED; unknown/unverifiable gives503 PROCESSING_FENCE_UNCERTAIN. A partial fence stays forever and the full16MiB remains held. A node becoming readonly/inactive fails closed with retained capacity; operator restoration or a later dedicated remediation design is required.

Only after both verified fences does the server insert an immutable `processing_review_commands` record. Its D1 guards recheck current Owner/session, scope, active node, exact review epoch and two distinct server-attested fenced kinds. Client fence proofs/keys are rejected by the strict API. In the same statement/transaction, job becomes `abandoned` with reserved_bytes0, workspace and node reservations each decrease16MiB, and the append-only event records confirming actor/session/request/UTC/before-after states. Original assets and used bytes stay unchanged. Audit failure rolls all D1 effects back; physical fences remain safe and recognized on retry. Exact committed retries return the same result, including after parent archive; changed payload or cross-operation actor/request reuse conflicts. All three existing ledgers have symmetric conflict guards and authorization precedes collision handling. Completed/unsupported/queued/running/retryable jobs cannot use this endpoint.
