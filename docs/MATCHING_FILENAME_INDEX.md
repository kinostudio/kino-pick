# Filename matching index — M3i1

## Scope and compatibility

This additive slice provides a real Owner-only status and bounded maintenance API/UI for derived canonical filename keys. It does **not** switch the existing version matcher to indexed queries, raise its 1,000-candidate safety limit, change Assisted target choices, enable filename rules, or implement batch upload. Those remain the next M3i slices, followed by the remaining M1–M5 work. Existing upload replay, quota, immutable versions, head CAS and album change-sequence guards remain authoritative.

The current reader materializes at most 1,000 version/pending-upload rows from an album and requires review when incomplete. This is safe but prevents automatic classification in large albums with unrelated rows. A trustworthy indexed reader first needs canonical keys and a completeness proof. SQLite `lower()` is not equivalent to the existing JavaScript NFC/case rules. Mutable `photos.original_filename` cannot become immutable historical filename evidence.

## Data and service

Migration `0049_matching_filename_index.sql` adds one derived append-only table and scoped lookup indexes/guards; no existing source row is backfilled or rewritten by migration. Each key belongs to one immutable upload session and profile `default-v1`, carries the original filename/scope witness, and is generated by the existing `canonicalizePhotoFilename` function. The default profile is NFC, case sensitive, without JPG/JPEG equivalence or suffix removal. Invalid canonical names are recorded explicitly so retries cannot loop forever. A future rules change needs a distinct versioned profile and complete rebuild; never reinterpret old rows with new semantics.

The insert guard binds the witness to the actual source session. Updates, deletes and differing replacements are rejected. Canonical text is computed by trusted Worker code; SQLite does not independently implement Unicode canonicalization. Administrative database access remains a trusted boundary and must not insert fabricated derived keys.

`D1MatchingFilenameIndex.read` checks current enabled Owner, live session, owned workspace and active project/album in the same SQL snapshot as counts. `advance` selects at most 24 missing session keys, computes canonical names in bounded JavaScript, inserts through D1 batch with current authority/source checks, and reads current status again. Concurrent exact derived inserts are idempotent. No client supplies a filename, key, profile, target photo or source session. Maintenance never creates a product audit action or changes valid-human-view retention, storage quota, files or version state.

## API and UI

- `GET /api/v1/matching-filename-index/capabilities`
- `GET /api/v1/albums/:albumId/matching-filename-index`
- `POST /api/v1/albums/:albumId/matching-filename-index`, strict empty JSON object, exact configured Origin, mandatory `X-Kino-Expected-Actor`, no query parameters, maximum 1,024-byte body.

All routes retain existing Owner API middleware and private/no-store responses. Status exposes scope UUIDs, fixed profile, aggregate counts and state only. `MATCHING_FILENAME_INDEX_ENABLED` defaults false everywhere and throws if enabled outside local. It independently gates maintenance and grants no upload, image, Guest or matching capability.

Status reports indexed/missing/invalid sessions, versions without an immutable upload completion witness, and photos without complete version/head evidence. `building` means missing keys remain; after those are filled, unresolved invalid/legacy/incomplete evidence yields `blocked`; only complete evidence yields `ready`. Counts use indexed relational queries but still inspect album coverage; representative-volume latency and edge CPU are not yet measured.

Readiness is a snapshot, not a lease. New source sessions make it incomplete again. Uploads are not dual-writing this index in M3i1. No automatic classifier may rely on a prior ready result. Future integration must bind exact profile, full-history evidence and pending uploads to the same authorized snapshot, retain reserve-time change-sequence/head CAS, and recheck completeness after concurrent writes. Legacy unlinked versions stay blocked until there is an explicit immutable forward-repair strategy; never silently ignore them.

The local Owner gallery offers explicit next-batch maintenance and refresh, with status/blocker explanations. It does not automatically loop. Private asynchronous results require matching current Owner and exact workspace/project/album, and are cleared on lifecycle suspension. Disabled capability renders no maintenance controls.
