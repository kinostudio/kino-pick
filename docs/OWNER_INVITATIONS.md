## API and UI

GET /api/v1/projects/:projectId/invites requires the current enabled Owner and live Owner session. It accepts only one optional cursor, returns at most24 summaries plus nextCursor, and repeats current authorization on the query/result. Unknown/foreign project404, missing Owner session401, disabled Owner403, malformed UUID/cursor/query400. All responses are private/no-store and no-referrer. Summaries include UUID/scope, access mode, twelve independent permissions, UTC creation/expiry/revocation, sealed flag, explicit album IDs/names, configured maxUses and lifetime issued-session count. No token, password/verifier, secret hash, Owner cookie or R2 key/URL appears. A sealed scope is not a claim that an expired invite is active; UI displays its UTC expiry separately.

POST /api/v1/invites/:inviteId/revoke accepts strict JSON {requestId:UUID,confirmRevoke:true}, current Owner/session and exact same-origin Origin. Returns {revocation:{inviteId,workspaceId,projectId,revokedAt}}. Confirmation false/missing/extra fields400, anonymous401, Owner/Origin denial403, unknown/foreign invite404, request conflict or a new request for an already-revoked invite409, unknown DB/service failure503. Body limit16KiB. No client actor/tenant/session ID is accepted. Revocation is allowed for archived parents and expired/unsealed invites: withdrawal must not depend on content being editable.

Project page → 客戶邀請 → 查看客戶邀請 loads actual metadata. Unchecked confirmation keeps 撤銷邀請 disabled. Successful revoke refreshes the list; no undo or original link/secret recovery is offered. Network/unknown-result failure retains the same in-memory request UUID for retry. Explicit refresh/reopen/reload reconciles canonical list state; it does not blindly create a new revoke. Pending IDs are not durable across reload, but an already-revoked item displays its committed state and no mutation button. GET refresh/paging, empty/error states, collapse and retry are functional. No automatic destructive operation or photo deletion occurs.

## Atomicity, audit and namespace

Migration0017 adds immutable invite_revocation_commands keyed by actor/request and unique per invite. Its INSERT guard authenticates the current Owner/session before conflicts/replay, checks all four prior ledgers, distinguishes payload/target conflict from exact replay, then checks ownership and existing revocation. Exact replay under another currently valid session of the same Owner returns the immutable original revocation time; disabled/expired/revoked Owner sessions cannot replay. New distinct requests after revocation deliberately409 INVITE_ALREADY_REVOKED, requiring canonical refresh. Concurrent identical requests create exactly one command/revocation/event.

The same INSERT creates guest_invite_revocations and its append-only share.revoked audit. Client request ID, actor, authorization session, workspace/project, invite ID and before/after revoked values are recorded; UTC event time is DB-generated. Audit failure rolls command+revocation back, preserving Guest access until an actually committed retry. Guest resolver checks invite revocations on every call, so existing sessions lose access immediately after commit without deleting session/history rows.

All four canonical prior guards are rebuilt with current auth → all other ledger collisions → local replay → resource checks. Sibling triggers may execute in unspecified order, so the new namespace check is deliberately inside each canonical guard before RAISE(IGNORE); redundant existing sibling guards remain. No old migrations/checksums are rewritten. New commands contain no bearer secret. Existing internal fixture revocations retain deterministic request IDs; future command-driven revocations use the matching client ID. Historical audit/revocation rows are never rewritten.
