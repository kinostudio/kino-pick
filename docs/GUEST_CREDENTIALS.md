## Password and bearer contract

guest-credentials.ts uses native node:crypto.scrypt with fixed N32768/r8/p3,32-byte key, random16-byte salt and maxmem64MiB. The persisted v1 shape is exactly $kino-scrypt$v=1$N=32768,r=8,p=3$ followed by32 lowercase salt hex, one dollar separator and64 lowercase key hex. Algorithm/cost/version cannot be selected by stored input. Unknown formats, cost changes, extra bytes, NULs, terminal newlines and malformed passwords are rejected. Fixed-length derived buffers use node:crypto.timingSafeEqual; the complete request is not promised constant-time.

Password input is12–256 UTF-16 code units, well-formed Unicode, at most1024 UTF-8 bytes. No trimming or Unicode normalization is performed; spaces and composed/decomposed strings are distinct. Mutable password/key buffers are cleared where held, without claiming secure erasure of immutable JS strings or native implementation memory. Native KDF failure throws the fixed GUEST_PASSWORD_KDF_UNAVAILABLE error; no cheaper algorithm, plaintext or plain-SHA fallback exists. Malformed verification returns false before KDF; future public exchange must combine generic denials, dummy-work policy and pre-KDF throttling rather than expose an account oracle.

generateGuestBearer creates32 independent CSPRNG bytes encoded as64 lowercase hex characters. Invite token hashes use SHA-256 over kino-pic:guest-invite-token:v1: plus canonical token; session hashing retains its existing kino-pic:guest-session:v1: domain. Both enforce exact64-character length, including rejection of the JavaScript regex final-newline edge. SHA-256 is used only for random bearer lookup, never password storage. No raw token/password is written to ledger/audit/log/browser storage or list responses by these primitives.

0018 constrains NEW password-mode invite inserts to the canonical verifier shape, with explicit instr(value,char(0)) rejection because SQLite text length stops at NUL. Existing invite/verifier rows are preserved unchanged. Format validation is not cryptographic proof: the future trusted issuer must derive the verifier itself from the raw password and never accept a caller-provided verifier. Legacy untagged values fail verification and need explicit revoke/recreate; never reinterpret them as plaintext or silently weaken parameters.

## Runtime evidence and deployment gate

OWASP lists N2^15/r8/p3 as a minimum scrypt option when Argon2id is unavailable. Cloudflare documents native Argon2 as unsupported and node:crypto APIs otherwise subject to listed exceptions. A Cloudflare workerd PR documents that local/open-source PBKDF2 limits can differ from hosted defaults; local600k success would not prove hosted compatibility. These sources informed selection, not a deployment claim.

Actual local workerd tests derive two fresh verifiers, cross-check the full derived key with Node scrypt at the same parameters, and accept exact/reject changed passwords. Host-observed wall samples are printed as synthetic metadata only and recorded in VERIFICATION. They are not Worker CPU, peak memory, load/concurrency, remote latency or free-tier acceptance. Approximate32MiB algorithm memory and maxmem64MiB are parameters, not measured isolate memory. Keep public KDF callers closed until throttling, bounded concurrency and the configured hosted plan are validated; do not lower work factor to force a free-plan claim. No KDF endpoint is added to the deployable Worker; the test probe is only in tests/storage-harness.ts.

References: [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt), [Cloudflare Node crypto](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/), [workerd PBKDF2 limit discussion](https://github.com/cloudflare/workerd/pull/7550), [SQLite NUL behavior](https://sqlite.org/nulinstr.html).

## Guest logout API

POST /api/guest/logout is separate from Owner middleware. It requires exact configured Origin, JSON and strict {requestId:UUID}, max16KiB. The only target proof is the canonical Guest cookie, never a submitted actor/session/invite ID. Local HTTP uses kino_guest; configured HTTPS uses __Host-kino_guest only. A valid secret resolves its exact hashed session, then inserts an immutable guest_logout_commands row. It can revoke itself after session/invite expiry, Owner disable or invite withdrawal; those gates must not prevent logout.

The SQL guard checks session/guest/hash proof before replay. Commands use the Guest actor namespace (guest_id,request_id), separate from Owner command identities, with a unique session. Exact replay is idempotent; reusing that guest/request for another session409 REQUEST_ID_CONFLICT. Future Guest action ledgers must extend this namespace before exposing writes. Existing revocation, including privileged historical fixture revocation, is already success and does not create another event. Anonymous/unknown/ambiguous cookies get the same200 {loggedOut:true} with no database mutation; no account/session metadata is exposed.

Command, session revocation and append-only guest.session_revoked audit commit together. Audit includes client request ID, Guest actor/session, workspace/project, invite ID, DB UTC time and before/after revoked state; no raw secret/hash/password. Audit failure rolls command/revocation back. The API confirms committed revocation before clearing the cookie;503 failures and409 conflicts do not clear it, preserving proof for retry. On success: Path=/; Max-Age=0; HttpOnly; SameSite=Lax, plus Secure and __Host- name on configured HTTPS, no Domain. Owner cookie and other Guest sessions are untouched. All responses remain private/no-store and no-referrer.400 invalid/extra input,403 Origin,413 oversized body,409 request conflict,503 unknown service result. No Owner auth required.

Actual Chromium tests inject synthetic HttpOnly cookies, drop the first committed logout response, prove the still-present cookie cannot access the album, then retry the same request ID. The second response removes only the Guest cookie and Owner API remains usable. This is backend/browser-cookie acceptance, not a Guest login UI or real HTTPS/provider acceptance. An additional configured-HTTPS Worker fixture verifies __Host-only parsing and response flags without claiming TLS deployment.
